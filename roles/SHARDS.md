# SHARDS — контракт workspace-files

Цей документ — джерело істини для того, **що в якому шарі живе** в системі CLAUDE.md ботів. Усі правки в `roles/_*.md`, `roles/<role>.md`, `bots/<name>/workspace-files/*.md` мають дотримуватись цього контракту. Без нього шари неминуче дрейфують у дублі і конфлікти.

## Принцип консолідації

> Для кожного концепту — **одне канонічне місце** з **максимумом прикладів**. Усі інші згадки — 1-рядковий pointer на канонічне місце.

Це означає:
- Економія байтів — з усунення структурних дублів, **не** з обрізки прикладів.
- Кількість few-shot прикладів має **зростати**, не зменшуватись.
- Розмір зібраного CLAUDE.md може зменшуватись на 40-50%, при цьому щільність прикладів зростає в 1.5-2×.

## Класифікація контенту (5 категорій)

Перед будь-якою правкою кожен блок класифікувати:

| Категорія | Що це | Дія |
|---|---|---|
| **Behavioral anchor** | Конкретна do/don't пара ("Не 'ви впевнені?', а 'видалити всі 47 файлів?'") | **Зберігати завжди**, не "оптимізувати" |
| **Few-shot trigger** | Фраза → tool → коли НЕ (`"намалюй" → GenerateImage`) | **Зберігати завжди**, переміщати в канонічне місце |
| **Rule without example** | Абстрактне правило ("Не комітити автоматично") | Зберігати, **доповнити прикладом** |
| **Mechanism description** | Опис як влаштована система зсередини (туторіал markdown, опис що Bash робить) | **Видаляти**, якщо модель і так знає |
| **Duplicate** | Те саме сказано в 2+ шарах різними словами | Залишити в канонічному shard, інші → 1-рядковий pointer |

## Контракт шарів (8 файлів)

| Shard | МАЄ містити | НЕ МАЄ містити | Розмір target |
|---|---|---|---|
| `IDENTITY.md` | Ім'я, emoji, 1-2 речення хто це | Будь-які правила, інструкції, формат | < 200 байт |
| `SOUL.md` (`_soul.md`) | Характер, цінності, етика, межі, meta-правила взаємодії, emoji legend | Tool routing, опис tools, markdown туторіал, опис механік | ~4 KB |
| `BOT_SOUL.md` | Лише **відмінності** від глобального SOUL. Або повна заміна з `<!-- REPLACES_GLOBAL -->` | Дублі global без необхідності | < 1 KB (без REPLACES_GLOBAL) або ~4 KB (з REPLACES_GLOBAL) |
| `ROLE.md` | Спеціалізація, доменні workflows, що бот вміє конкретно | Generic tool routing, character | ~1 KB |
| `TOOLS.md` (`_tools.md`) | Master tool routing table, drilldown секції з прикладами, AskUser, Memory, Команда, Workspace | Character, group chat, dev planning, markdown туторіал | ~8 KB |
| `BOT_TOOLS.md` | Лише **role-specific** tool routing, якого нема в global | Дублі global TOOLS | < 1 KB |
| `USER.md` | Сталий профіль: ім'я, мова, timezone, контекст, top-level вподобання | Динамічні дані (це SaveFact + MEMORY + Calendar) | < 1 KB |
| `MEMORY.md` | Курована мета-пам'ять: правила-уроки, патерни, прийняті рішення з "тому що" | Сирі факти, профіль, активні задачі | ~2 KB |

## Канонічна мапа топіків

Для кожного концепту — точно одне місце канонічного опису:

| Топік | Канонічний shard | Дозволені згадки в інших |
|---|---|---|
| Character / values / ethics | `_soul.md` | BOT_SOUL — лише дельта |
| AskUser meta-правило | `_tools.md → ## AskUser` | `_soul.md`: 1 рядок-інваріант + посилання |
| Memory architecture (USER/MEMORY/SaveFact) | `_tools.md → ## Пам'ять` | `_soul.md`: 1 абзац |
| CreateReminder + cron режими | `_tools.md → ## Нагадування` | role TOOLS — лише domain examples |
| Tool routing master table | `_tools.md → ## Tool routing` | role TOOLS — лише role-specific рядки |
| Workspace files механіка | `_tools.md → ## Workspace` | none |
| Команда / ask_manager | `_tools.md → ## Команда` | none |
| Group chat protocol | `_soul.md` всередині `<!-- IF GROUP_CHAT_ENABLED -->` | none |
| Git workflow | `_soul.md` всередині `<!-- IF GIT_ACCESS_ENABLED -->` | none |
| Dev planning procedure | `_soul.md` всередині `<!-- IF DEV_MODE_ENABLED -->` | none |
| Markdown formatting | none — модель знає | 1 рядок у TOOLS |
| Domain expertise | `roles/<role>.md → ROLE` | none |

**Правило вирішення суперечок**: якщо концепт описано в двох місцях — застосовується таблиця вище. Не-канонічне місце видаляється або замінюється на pointer.

## Conditional sections (`<!-- IF FEATURE -->...<!-- END -->`)

Капабіліті, які потрібні не всім ботам, інлайн-блоки в `_soul.md` (та потенційно `_tools.md`):

```markdown
<!-- IF DEV_MODE_ENABLED -->
## Технічні задачі (планування коду)
[повний контент з прикладами і кроками]
<!-- END -->
```

Прапорці в `bots/<name>/.env`:
- `GROUP_CHAT_ENABLED=0|1` — групові Telegram-чати
- `DEV_MODE_ENABLED=0|1` — режим планування коду, AskUser перед змінами
- `GIT_ACCESS_ENABLED=0|1` — git workflow, коміт-конвенції

Асемблер читає `.env`, фільтрує блоки, маркери видаляє з виводу. Деталі — `src/workspace-files.ts → assemble()`.

## Hierarchy markers як emoji

Маркерами обов'язковості виступають **лише emoji**, без текстових тегів. Розшифровка дається один раз у legend на початку `_soul.md`:

| Emoji | Значення |
|---|---|
| 🔒 | інваріант, ніколи не порушуй |
| 💡 | рекомендація, можна відступити з обґрунтованої причини |
| 🎯 | приклад використання |
| ✅ | правильний патерн |
| ❌ | анти-патерн |
| 📌 | фонова інформація / контекст |

Використання — лише emoji, без слів:

```markdown
🔒 AskUser завжди коли чекаєш відповіді користувача.

💡 Voice messages зазвичай вимагають коротших відповідей.

🎯 "Який рецепт?" → AskUser(["Класичний", "Вегетаріанський"])

❌ "Чудове питання!"
✅ просто відповідь
```

## Структура drilldown секції

Кожна `## ToolName` секція в `_tools.md` має містити:

1. **Призначення** — 1 речення.
2. **Параметри** — якщо нетривіальні.
3. **Decision tree** — якщо є вибір режимів (з `🔒` для інваріантів).
4. **Examples (positive)** — мінімум 3-5 прикладів у форматі таблиці `User | Call`.
5. **Common mistakes** — таблиця `User | ❌ | ✅` з 2-3 рядками.
6. **Не для** — список контр-показань.

Це гарантує мінімальну щільність behavioral сигналу для кожного складного інструмента.

## Lint правила (автоматично перевіряються)

Тести в `src/workspace-files-contract.test.ts`:

1. **No duplicate h2** — жоден `## ...` не з'являється у зібраному CLAUDE.md двічі.
2. **No tool over-mention** — кожне ім'я tool згадане ≤2 рази.
3. **All `## ToolName` sections have ≥3 examples**.
4. **Behavioral anchors counted** — у зібраному файлі ≥10 пар `❌`/`✅`.
5. **Few-shot density** — мінімум 40 прикладів у пілотному ai.
6. **All `<!-- IF X -->` markers removed** після збірки.

Адмінка попереджає при редагуванні BOT_SOUL/BOT_TOOLS, якщо overlay ≥80% дублює global.

## Як додавати нові правила

1. Класифікуй за 5 категоріями вище.
2. Знайди топік у канонічній мапі — додай у канонічний shard.
3. Якщо топіка нема — додай новий рядок у мапу разом з правкою.
4. Якщо це capability-залежне — оберни в `<!-- IF FEATURE -->...<!-- END -->`.
5. Якщо це behavioral anchor — додай і `❌`, і `✅` варіанти.
6. Запусти `npm test` — contract-тести мають проходити.
