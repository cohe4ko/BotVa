**Відхилення від плану під час реалізації:**

- Лог (планована Фаза 3) увійшов у першу поставку разом із з'єднанням — MCP-інструменти `tg_list_chats`/`tg_search` без нього не мають по чому працювати, а розділ адмінки був би порожній.
- `tg_people` і медіа-завантаження відкладені: для читання, непрочитаних і відправки вони не потрібні, а потрібні стануть на етапі витягу фактів, де ідентичність співрозмовника критична.
- Замість `PROJECT_ROOT` через `envPassthrough` shim визначає корінь від власного шляху — боти не експортують цю змінну в середовище MCP-сервера.
- Логін живе в процесі адмінки, а не демона: першої авторизації демон ще не переживе, бо без сесії він не має чого тримати.

Схему писали до автовідповідача, який уже задав цю форму: у бота є `BOT_DIR`, модель з адмінки, ключі, `insertFactForBot` і `reminders`, а в демона немає нічого з цього. Демон лишається тим, чим був — однією MTProto-сесією і логом. Обидва процеси читають `store/telegram.db` напряму.
- **Право на забуття не реалізоване** — свідоме рішення власника (6.09.2026): це приватний інструмент, а не сервіс, і все отримане лишається. `/tg forget` викреслено з плану.
- **Аналіз вмикається окремо від логування.** Спека мала один прапорець `sensitivity`; на практиці режим чату і бот-приймач розділені: `tg_chats.mode` вирішує, що логувати й що дозволено витягати, `tg_chats.target_bot` — чи витягати взагалі і в чию пам'ять. Логувати чат і писати його вміст у довгу пам'ять бота — різні дозволи.
- **Дедуплікація в межах одного розбору.** Модель стабільно повертає той самий дедлайн двічі — як обіцянку і як дату, з тієї ж цитати. Промт просить одну; `dedupeItems()` це гарантує, бо промт — прохання, а не контракт.

## Задача

Агент бачить переписку власника в Telegram і перетворює її на:

1. **Факти** в пам'яті бота — знаходяться через наявний гібридний пошук і самі інжектяться в контекст.
2. **Задачі й нагадування** в наявній таблиці `reminders` — спрацьовують, а не лежать текстом.
3. **Архів** сирих повідомлень — щоб знайти дослівну цитату за березень.

Ключова вимога, якої не було в попередньому плані: **реагувати на вихідні повідомлення власника**. Вихідне «зроблю до п'ятниці» — це зобов'язання, найцінніше джерело задач. Вхідне «зроби X» — лише чужий запит.

## Центральне рішення

Telegram — це **ще одне джерело для наявного конвеєра дистиляції BotVa**, а не окрема система.

BotVa вже має повний ланцюг «сирий потік → факти в пам'яті»:

| Етап | Файл | Що перевикористовуємо |
|---|---|---|
| Аналіз чанку | `src/listener-analyze.ts` | патерн промту, `normalizeTopic`, `getBackgroundModel` |
| Черга ревізії | `src/listener-facts.ts` | pending/approved/declined, `getReviewStats` |
| Запис у пам'ять | `src/admin/db-multi.ts:67` | `insertFactForBot` — insert + embedding + auto-link |
| Пошук | `src/vector-search.ts` | `searchFactsHybrid` — FTS5 + вектор + spreading activation |
| Проактивна подача | `src/memory.ts` | `buildMemoryContext` — факти самі йдуть у контекст |
| Нагадування | `src/db.ts:270`, `src/scheduler.ts` | `reminders` з `remind_at`, `run_agent`, `schedule` |
| Прецедент демона | `scripts/orange-pi-listener/receive-transcript.ts` | окремий launchd-процес, який пише в конвеєр |

Ми не пишемо другу пам'ять, другий пошук і другу чергу. Ми додаємо джерело.

## Стек: GramJS, не Telethon

Рекомендація — `telegram` (GramJS, MTProto для Node) замість Python + Telethon.

**Чому:** один процес замість двох, той самий TypeScript, прямий виклик `insertFactForBot`/`embed`/`analyzeConversation` без HTTP-стрибка між мовами, деплой через наявний `scripts/deploy.sh`, тести через vitest поруч із кодом, без venv і без `requirements.txt`.

**Ціна:** GramJS документований гірше за Telethon, спільнота менша. Ризик локалізований у тонкому шарі «підключитись і читати апдейти» — якщо він виявиться проблемним, шар замінюється на Python-міст без переписування конвеєра.

## Три яруси моделей

| Ярус | Що робить | Вартість | Коли спрацьовує |
|---|---|---|---|
| **Tier 0** | Скоуп чату, sensitivity, довжина, службові повідомлення, виключення ботів BotVa | 0 | на кожне повідомлення |
| **Tier 1** | `analyzeConversation()` на буфер-чанк, background-модель (Haiku) | ~цент за чанк | раз на розмову |
| **Tier 2** | Повний агент із контекстом бота через `runAgent` | дорого | тільки коли Tier 1 просить дію чи уточнення |

Tier 1 бере модель із `getBackgroundModel(chatId)` — вона вже налаштовується в адмінці, окремої змінної не заводимо.

## Одиниця аналізу — розмова, не повідомлення

Telegram — потік реплік по три слова. «так, давай» без попередніх п'яти рядків не означає нічого, а аналіз поштучно і дорогий, і безглуздий.

Буфер flush'иться коли настає перше з:
- 4 хвилини тиші в чаті,
- 25 повідомлень у буфері,
- 30 хвилин від першого повідомлення в буфері (щоб довга нескінченна розмова не висіла).

Мінімальний інтервал між flush одного чату — 60 секунд.

Чанк, що йде в Tier 1, містить: назву чату, тип, список учасників із канонічними іменами й ролями, кожну репліку з напрямком (`Власник →` / `← Петро`), час, `msg_id`, і текст reply-цитати, якщо є.

## Що витягає Tier 1

```jsonc
{
  "facts":              [], // знання → sector=semantic
  "events":             [], // що сталося → sector=episodic
  "commitments_mine":   [], // власник пообіцяв → задача + нагадування
  "commitments_theirs": [], // власнику пообіцяли → нагадати перевірити
  "requests":           [], // власника попросили → задача-кандидат
  "dates":              [], // зустріч / дедлайн → нагадування
  "contacts":           []  // нова людина, реквізити → факт
}
```

Кожен елемент:

```jsonc
{
  "text": "...",              // дистильоване формулювання
  "who": "Вікторія",          // канонічне ім'я, не "він"
  "confidence": 0.82,         // 0..1
  "when_due": "2026-09-05T15:00",  // ISO або null
  "topic": "home",            // одне англійське слово, normalizeTopic
  "tags": "...",              // двомовні, як у listener
  "quote": "...",             // дослівна цитата — audit trail
  "msg_ids": [12345, 12346]   // для зв'язку з логом і обробки edit/delete
}
```

`quote` і `msg_ids` — обов'язкові. Без них не можна ані перевірити факт, ані інвалідувати його при редагуванні джерела.

**Вихідні й вхідні мають різну семантику в промті.** Вихідне «зроблю до п'ятниці» → `commitments_mine`. Вхідне «зроби до п'ятниці» → `requests`. Це різні речі з різними наслідками, і промт має розрізняти їх явно, а не мати один фільтр «є ознаки доручення».

## Гейт впевненості

| Впевненість | Факт | Задача / нагадування |
|---|---|---|
| ≥ 0.75 | `insertFactForBot` одразу | створюється, якщо є `when_due` |
| 0.45 – 0.75 | у чергу ревізії | у чергу ревізії |
| < 0.45 | drop | drop |

Задача без `when_due` ніколи не створює нагадування автоматично — іде в чергу, де ти проставляєш дату.

**Дедуплікація перед вставкою.** Одна домовленість згадується в переписці по п'ять разів. Перед `insertFactForBot` — embedding кандидата проти наявних фактів бота; при cosine > 0.9 факт не вставляється, а наявному піднімається `usefulness` (механізм `BoostFact` уже є). Для задач — те саме плюс перевірка збігу `when_due` ±1 день.

## Дві пам'яті з явним контрактом

| Рівень | Де | Чим шукає бот | Для чого |
|---|---|---|---|
| **Знання** | `facts` бота-приймача | `SearchMemory` (гібрид) + автоінжекція в контекст | «що я знаю про ремонт даху» |
| **Архів** | `store/telegram.db` | `SearchTelegram` (новий builtin tool) | «що саме я писав Петру про ціну в березні» |

Правило маршрутизації йде в `BOT_TOOLS.md` бота-приймача: за замовчуванням шукати в пам'яті; лізти в архів тільки коли потрібна дослівна цитата, хронологія переписки або підтвердження «хто що сказав».

`SearchTelegram` читає `store/telegram.db` напряму в read-only режимі — без мережі й без MCP. Живі дії (надіслати, підтягнути свіжий чат, скачати медіа) йдуть через MCP до демона.

### Транспорт: Unix socket, не TCP

TCP-порт на `127.0.0.1` довелося б захищати окремо — його бачить будь-який процес користувача. Unix socket захищений файловими правами (600), тобто тим самим механізмом, що вже стереже `telegram.session`. Плюс це наявний патерн BotVa: `mcp-servers/colleague` і `mcp-servers/manager` — це stdio-сервери, які всередині ходять у `colleague.sock` (`mcp-servers/colleague/src/index.ts:28`).

```
Агент бота
   │  stdio (JSON-RPC, newline-delimited)
   ▼
mcp-servers/telegram/  — shim, ~30 рядків
   │  net.connect('store/telegram.sock')
   │  stdin → socket, socket → stdout
   ▼
botva-telegram — MCP Server поверх сокета
```

Shim — **чистий pipe**, а не другий опис тулів:

```ts
const client = net.connect(SOCK_PATH)
process.stdin.pipe(client)
client.pipe(process.stdout)
```

MCP над stdio і є newline-delimited JSON-RPC, тому той самий фреймінг ходить через сокет без перекладу. Схеми тулів живуть **тільки в демоні** — додав тул, і він доступний без ребілду shim'а. `colleague-mcp` описує тули в себе, бо в нього на тому кінці не MCP-сервер, а прикладний протокол; у нас на тому кінці MCP, тому дублювати схеми немає потреби.

Деталі:
- сокет `store/telegram.sock`, права 600, знімається при graceful shutdown і перестворюється на старті (як `src/index.ts:26`);
- демон тримає **окремий інстанс MCP Server на кожне з'єднання** — кілька ботів можуть працювати паралельно;
- демон не запущений → shim віддає зрозумілу помилку («Telegram Observer не запущений»), а не висить до таймауту, за зразком `colleague-mcp`;
- запис у `mcp-servers.json`:

```json
"telegram": {
  "command": "node",
  "args": ["mcp-servers/telegram/build/index.js"],
  "envPassthrough": ["PROJECT_ROOT"],
  "enabled": true
}
```

## Гейт вихідних дій

Чотири незалежні бар'єри, бо це дії від імені живої людини:

1. **AskUser перед кожним відправленням.** Бот генерує чернетку в стилі власника (пряме «ти», без канцеляризмів, коротко) → показує → `[Надіслати / Правити / Скасувати]`. Наосліп нічого не йде.
2. **Allowlist адресатів.** Дефолт — тільки Saved Messages. Кожен новий адресат додається вручну в адмінці. Порожній allowlist не означає «можна всім».
3. **Rate limit.** Максимум 10 вихідних на годину, 30 на добу. Перевищення — жорстка відмова, не черга.
4. **Audit.** Кожна вихідна дія в `audit_log` (`src/db.ts:124`) з повним текстом, адресатом і хто підтвердив.

## Приватність третіх осіб

Логувати всі приватні чати за замовчуванням означає скласти в пам'ять бота чужі діагнози, фінанси й інтимне листування. Allow/blocklist на рівні чату цього не покриває.

**Рівні чутливості на чат** (`tg_chats.sensitivity`):

| Рівень | Лог | Витяг фактів | Для чого |
|---|---|---|---|
| `full` | ✅ | ✅ + задачі + дії | робочі чати, сім'я |
| `facts-only` | ✅ | ✅ факти, ❌ задачі | дефолт для приватних |
| `log-only` | ✅ | ❌ | видно в архіві, нічого не потрапляє в пам'ять |
| `ignore` | ❌ | ❌ | повністю поза системою |

**Дефолти за типом чату:**

| Тип | Дефолт |
|---|---|
| Приватний 1:1 | `facts-only`, але новий чат спершу питає |
| Базова група | `facts-only` |
| Супергрупа | `ignore` |
| Канал | `ignore` |
| Чат із будь-яким ботом BotVa | `ignore` — **жорстко, без винятків** |

**Автопідказка.** Новий чат, якого нема в `tg_chats`: перші повідомлення логуються як `log-only`, боту-приймачу йде нотифікація «Новий чат з X — який режим?» з кнопками. Рішення записується і більше не питається.

**Стоп-теми.** Глобальний список категорій, які не витягуються в жодному режимі: медичні дані третіх осіб, паролі й ключі, банківські реквізити інших людей, чужі особисті кризи. Йде в промт Tier 1 як явна заборона.

**Право на забуття.** `source` факту пишеться як `telegram:<chat_id>`, тому команда `/tg forget <chat>` видаляє одним рухом: усі повідомлення чату з логу, всі факти з цим `source`, усі похідні нагадування. Без цього поля видалення довелось би робити вручну по одному `DeleteFact`.

## Ідентичність співрозмовників

«Приїду в четвер» від дружини і від підрядника — різні факти з різними наслідками. Без ідентичності модель напише «він сказав, що приїде», і факт стане сміттям.

Таблиця `tg_people`: `peer_id`, канонічне ім'я, роль (дружина, підрядник, замовник), алаяси, нотатка. Seed — з Telegram-контактів при першому запуску, далі редагується в адмінці. Список учасників чату інжектиться в промт Tier 1 разом із чанком.

## Бюджет і гальма

24/7 на живому акаунті — це тисячі повідомлень на добу. Без стелі вартість стане невидимою.

- `TELEGRAM_DAILY_BUDGET_USD` — дефолт `1.00`.
- Лічильник у `tg_budget`, кожен виклик Tier 1 і Tier 2 пишеться туди ж, куди `usage_log`.
- 80% бюджету — нотифікація власнику.
- 100% — деградація: логування триває, аналіз зупиняється до півночі. Не тиха відмова — повідомлення в чат.
- Незалежний rate-limit Tier 1: максимум 40 викликів на годину.
- **Tier 2 через `colleague.sock` — максимум 5 на годину.** Сокет (`src/index.ts:25`) не має ані автентифікації, ані ліміту; кожен запис породжує окремий `runAgent`. Сплеск у 50 повідомлень за хвилину без ліміту = 50 паралельних агентів на одному боті.

## Ідемпотентність, редагування, видалення

- **Курсор.** `tg_cursor(chat_id, last_msg_id)`. Рестарт демона → GramJS віддає catch-up → без курсора отримуємо дублі фактів.
- **Витяги.** `tg_extractions` зв'язує діапазон `msg_ids` із тим, що з нього витягнули (`fact_id`, `reminder_id`). Один діапазон аналізується один раз.
- **Редагування.** Прийшов `MessageEdited` для `msg_id`, з якого вже витягнули факт → факт позначається `stale` і йде в чергу ревізії з поміткою «джерело змінилось». Не видаляється мовчки.
- **Видалення.** `MessageDeleted` → текст у логу замінюється на tombstone, похідні факти → `stale` + черга. Видалене повідомлення в архіві лишається як факт існування, але без вмісту.

## Ретроспектива — те, заради чого це все

Найцінніше в асистенті з-за плеча — не push «схоже, тобі дали задачу», а вечірній підсумок і виявлення того, чого **не сталося**.

**Щоденний дайджест, 21:00** — через наявний `reminders` з `run_agent=1`:
> Telegram за сьогодні: 3 обіцянки (2 з дедлайном), 1 запит без відповіді, новий контакт — Сергій, покрівельник.

**Щотижневий прохід по відсутності** — те, чого жоден логер не робить:
- `commitments_mine` без ознак виконання і з дедлайном, що минув;
- питання до власника без відповіді понад 48 годин;
- чат, який раптово затих після активної фази;
- `commitments_theirs`, за якими минув термін — нагадати, що тобі винні.

Це вливається в наявний ритуал консолідації (`src/consolidate.ts`, `scripts/weekly-review.py`), а не будує свій.

## Схема БД — `store/telegram.db`

```sql
tg_messages     (id, chat_id, msg_id, peer_id, direction, sender_name,
                 text, media_type, media_path, reply_to_msg_id,
                 ts, edited_ts, deleted_ts, embedding BLOB)
tg_messages_fts FTS5 (text)

tg_chats        (chat_id PK, title, type, sensitivity, target_bot,
                 decided_at, last_flush_ts)

tg_people       (peer_id PK, canonical_name, role, aliases, note, last_seen_ts)

tg_cursor       (chat_id PK, last_msg_id)

tg_extractions  (id, chat_id, msg_ids JSON, kind, target_bot,
                 fact_id, reminder_id, confidence, status, created_at)

tg_budget       (date PK, tier1_calls, tier2_calls, cost_usd)

tg_outbox       (id, chat_id, text, approved_by, sent_at, msg_id)
```

БД на рівні проєкту, не бота — бо один демон обслуговує кілька ботів-приймачів. Запис у пам'ять іде через `insertFactForBot(bot, ...)`, як це вже робить адмінка на approve з listener (`src/admin/routes/records.ts:929`).

## Адмінка — нова вкладка Telegram

| Розділ | Що там |
|---|---|
| Чати | список, тип, sensitivity, бот-приймач, обсяг логу; зміна режиму |
| Люди | `tg_people`, редагування канонічних імен і ролей |
| Черга | Tinder-ревізія кандидатів 0.45–0.75, як у Records |
| Витяги | що і звідки витягнули, з цитатою і посиланням на факт |
| Бюджет | витрати за день/тиждень, лічильники ярусів |
| Метрики | precision автозапису, % задач, що виконались |
| Outbox | історія вихідних дій із підтвердженнями |

## Метрики успіху

Без них поріг впевненості нема по чому калібрувати, а асистент, який помиляється в половині випадків, гірший за відсутність асистента — йому перестають вірити на другому тижні.

| Метрика | Як міряємо | Ціль |
|---|---|---|
| Precision автозапису фактів | частка автозаписаних фактів, які не видалено через `DeleteFact` за 30 днів | ≥ 85% |
| Precision задач | частка створених задач, які власник підтвердив або виконав | ≥ 70% |
| Recall | ручний аудит: 20 випадкових розмов на місяць, скільки реальних задач пропущено | ≤ 20% пропусків |
| Вартість | середня на добу | ≤ $0.50 |
| Обсяг черги | pending у черзі ревізії | ≤ 15 на тиждень |

`getReviewStats` (`src/listener-facts.ts`) уже рахує approved/declined — база для перших двох. Не проходить ціль — піднімаємо поріг, а не миримося з шумом.

## Фази

Порядок: спершу **обв'язка** — з'єднання, авторизація, інструменти, які бот викликає руками. Тільки коли це працює й перевірене — конвеєр автоматичного осмислення.

Так рано ловляться найризикованіші невідомі (чи витримає GramJS, як поводиться авторизація, чи стабільна сесія), і бот стає корисним ще до всякої автоматики. Лог іде вже у Фазі 1 — не тому що він частина конвеєра, а тому що без нього `SearchTelegram` шукати нема по чому, а тиждень реального логу дає цифри для калібрування Фази 3.

**Фаза 1 — з'єднання і сесія**
1. `src/telegram/` — модуль, GramJS-клієнт, обгортка над MTProto.
2. `login.ts` — одноразова авторизація: номер → код → 2FA. Автоматизувати не можна, Telegram вимагає код.
3. Зберігання сесії: `store/telegram.session`, права 600, gitignore, документована процедура відкликання.
4. Демон: `scripts/start-telegram-observer.sh` + launchd `com.botva.telegram-observer`, за зразком listener-receiver. Пережиток розриву зв'язку, авто-reconnect, pidfile.
5. Health-endpoint і статус у адмінці (System), як у listener.

*Ціль: процес живе добу без падінь і без повторної авторизації.*

**Фаза 2 — MCP-обв'язка**
6. MCP Server у демоні поверх Unix socket `store/telegram.sock` (права 600, інстанс на з'єднання).
7. Читання: `tg_list_dialogs`, `tg_read_chat`, `tg_get_history`, `tg_download_media`, `tg_resolve_contact`.
8. `mcp-servers/telegram/` — stdio-shim (pipe stdin↔socket) за зразком `mcp-servers/colleague`; запис у `mcp-servers.json` як звичайний stdio.
9. Відправка: `tg_send_message`, `tg_send_photo`, `tg_send_file` — одразу з чотирма бар'єрами гейту (AskUser, allowlist адресатів, rate-limit, audit). Allowlist на старті — тільки Saved Messages.
10. `tg_outbox` + вкладка Outbox у адмінці.

*Ціль: бот на прохання читає чат, знаходить контакт, і після твого підтвердження надсилає повідомлення. Уже корисно, автоматики нема.*

**Фаза 3 — лог і архів**
11. Схема `store/telegram.db`, міграції за патерном `src/db.ts`.
12. Tier 0: скоуп чату, sensitivity, виключення ботів BotVa, шум.
13. Пасивний лог `tg_messages` + FTS5, `tg_cursor` для ідемпотентності, обробка edit/delete.
14. `tg_chats` + автопідказка на новий чат, `tg_people` + seed контактів.
15. Builtin tools по архіву: `SearchTelegram`, `TelegramChatHistory`, `TelegramContacts`.
16. Вкладки Чати і Люди в адмінці.

*Ціль: тиждень тільки логувати. Побачити реальні обсяги, порахувати вартість Tier 1 на живих цифрах, відкалібрувати скоуп.*

**Фаза 4 — осмислення**
17. Буферизація розмов (debounce по чату).
18. `src/telegram/analyze-conversation.ts` — промт Tier 1 із розділенням вхідних і вихідних.
19. Гейт впевненості + дедуплікація через embedding.
20. Router chat → bot, запис через `insertFactForBot` і `createReminder`.
21. Черга ревізії + вкладки Черга і Витяги в адмінці.
22. Бюджет, лічильники, деградація при вичерпанні.
23. Tier 2 через `colleague.sock` із rate-limit.

**Фаза 5 — ретроспектива**
24. Щоденний дайджест 21:00.
25. Щотижневий прохід по відсутності (борги, тиша, прострочене).
26. Дашборд метрик, калібрування порогів за реальними даними.
27. Дзеркало в `~/TASKS.md`.

## Ризики

| Ризик | Оцінка | Мітигація |
|---|---|---|
| Шум у пам'яті вбиває проактивну інжекцію | **Високий** — головний ризик | Фази 1–3 без витягу, гейт впевненості, дедуп, метрика precision із порогом |
| Вартість виходить з-під контролю | Середній | Тижневий вимір на реальних обсягах у Фазі 3, перед вмиканням Tier 1, денний бюджет із деградацією |
| Петля «бот пише → userbot читає → факт про факт» | Високий, якщо не передбачити | Жорсткий `ignore` на всі чати з ботами BotVa за user_id, на рівні Tier 0 |
| Чужі приватні дані в пам'яті | Середній | Рівні чутливості, стоп-теми, автопідказка на новий чат, `/tg forget` |
| Обмеження акаунту | Низький при пасивному читанні | Без бекфілу на старті, вихідні через rate-limit, без масових дій |
| Компрометація сесії | Середній наслідок | Права 600, gitignore, FileVault, документована процедура відкликання (Telegram → Devices). Шифрувати файл сесії ключем із того ж диска — самозаспокоєння, а не захист; чесніше не робити вигляд |
| GramJS виявиться сирим | Середній | Перевіряється у Фазі 1, до будь-яких вкладень у конвеєр. Шар підключення тонкий і ізольований — заміна на Python-міст не чіпає решту |
| Дублі при рестарті | Високий без курсора | `tg_cursor` разом із логом у Фазі 3, `tg_extractions` разом із витягом у Фазі 4 — не потім |

## Свідомо не робимо

- **Бекфіл історії.** Ризик обмежень плюс вартість аналізу архіву, при тому що фільтри ще не відкалібровані. Коли знадобиться пошук по історії — окремий разовий імпорт у `tg_messages` **без витягу фактів**.
- **Другий пошук.** Нічого схожого на `searchFactsHybrid` не пишемо, `SearchTelegram` — це FTS по архіву, інший рівень.
- **Власний UI ревізії.** Розширюємо наявний патерн Records, а не будуємо паралельний.
